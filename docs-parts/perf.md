## 雇佣兵大规模战斗的性能审计（perf）

### 目标
雇佣兵加入后，检查"几百只怪 + 6 个兵 + 粒子"的逻辑步和渲染帧耗时，找热点，在**行为逐位不变**的前提下做低风险优化。

### 基准工具
- `tools/perf-merc.js`（新）：`node tools/perf-merc.js [logic|render|all]`。`logic` 在无头 Node 下跑第 40 / 100 / 150 关各 60 秒游戏时间（弱英雄 + 不倒城墙让怪堆起来，自动雇兵，兵上限 6）；`render` 用 Playwright 软件渲染，快进 40 秒后统计 `renderer.render` 单帧 JS 耗时和 `drawMercs` 单独耗时（`FRAMES` 环境变量控制帧数，默认 120）。
- `tools/perfkit.js`（新）：基准和回放测试共用的战斗构造器。
- 注：仓库里早已有 `tools/perf.js`（v0.26，无兵的渲染帧间隔基准），没有覆盖它。

### 热点（`node --cpu-prof`，第 40/100/150 关逻辑 60 秒）
自耗时占比：`updateMonsters` 23%、`step`（内联了英雄 / 弹道等）23%、GC 14%、`updateMercs` 9%、`isTargetable` 4%、`mercPickTarget` 3.7%、`mercTargets` 3.6%、`monsterSpeed` 3.5%、`mercBlockerFor` 1.9%、`rankTargets` 1.1%。雇佣兵相关合计约 20%，其中 `mercTargets` 每个兵每步分配一个数组是 GC 的一部分来源。

### 做了什么（规则 / 数值完全没动）
1. `mercPickTarget`：把 `mercTargets` 的筛选内联进循环，不再每个兵每步分配数组；筛选条件和遍历顺序不变（先到先得的 `<` 比较保持）。
2. `mercBlockerFor`：`updateMonsters` 开头把活着的兵按车道分桶（桶内顺序 = `this.mercs` 顺序），拦截判定只扫本车道；桶只在 `updateMonsters` 期间存在，外部直接调用 `mercBlockerFor` 仍走原来的全量遍历。兵为 0 时不建桶，零开销。
3. `drawMercs`：`litSprite` 缓存键原来是 `Math.random()`（每帧每个兵都重画光影精灵）。改为"动画帧（按 `LIT_FPS`=12 取整）+ 状态 / 受击闪光 / 冲锋 / 蓄力 / 死亡渐隐量化"，和怪物同一套节奏。画面上兵的动画从每帧刷新变成约 12 帧/秒刷新（怪物一直如此）。
没动：`rankTargets`（每次一个 `sort`，但调用频率低，改它收益小、风险大）。

### 结果（本机，同一台机器交替运行取典型值；机器负载波动大，单次数字有 ±20% 噪声）
逻辑步耗时（ms / 步，无头 Node）

| 关卡 | 怪物峰值 | 兵峰值 | 优化前平均 / P95 | 优化后平均 / P95 |
|---|---|---|---|---|
| 40 | 169 | 6 | 0.26 / 0.40–0.45 | 0.23–0.26 / 0.34–0.38 |
| 100 | 444 | 5 | 0.23–0.28 / 0.40–0.44 | 0.24–0.29 / 0.40–0.54 |
| 150 | 308 | 5 | 0.19–0.25 / 0.35–0.40 | 0.21–0.34 / 0.36–0.40 |

渲染（ms / 帧，软件渲染，3 次交替取范围；该基准里兵会战死，场上平均 3–5 个）

| 关卡 | render 平均 前 → 后 | drawMercs 平均 前 → 后 |
|---|---|---|
| 40 | 7.5–7.8 → 8.9–9.8 | 0.78–0.83 → 1.08–1.13 |
| 100 | 11.0–13.1 → 11.7–13.4 | 1.97–2.33 → 0.72–0.92 |
| 150 | 12.8–13.4 → 12.6–13.6 | 1.67–2.01 → 0.81–0.87 |

### 诚实的结论
- **逻辑层没有可测的收益**：一步只要约 0.25 ms（60 FPS 预算 16.7 ms 的 1.5%），雇佣兵相关只占其中约 20%，优化后的差异淹没在噪声里（P95 / 最大值主要是 GC 和出怪尖峰）。这些改动主要是减少分配、让复杂度从 O(怪×兵) 降到 O(怪×同车道兵)，在 6 个兵 / 几百只怪时不足以拉开差距。
- **渲染层 `drawMercs` 在第 100 / 150 关约降一半（约 1.0 ms/帧）**，但整帧 `render` 平均没有可见变化（总 8–13 ms，主要是怪物与背景），第 40 关的数字反而偏高，属于噪声（兵数 / 怪数每次运行略不同）。
- 早先在机器严重过载（负载 60+）时测到的 `drawMercs` 19–46 ms 是争抢 CPU 的假象，不能当结论。
- 性能瓶颈在别处（`updateMonsters` 自身循环、怪物绘制），不是雇佣兵；要继续提速应优化怪物逻辑 / 绘制，不属于本次范围。

### 验证了什么
- `tests/feat-perf.test.js`：第 40 / 100 / 150 关、固定种子、20 秒，每帧记录怪物 hp 总和 + 怪物数 + 每个兵的 `x,y,hp,state,dead` 以及兵击杀 / 阵亡 / 军饷，SHA-256 哈希；基线哈希在优化**之前**用未改动代码记录，优化后逐位一致（并断言场上确有兵和一批怪）。另有无兵回放自洽性检查。
- `tests/game.test.js` 全部通过。

### 没验证什么
- 没有在真机 / 带 GPU 的浏览器上测帧率；渲染数字是 Playwright 无头软件渲染里 `render()` 调用的 JS 耗时，GPU 提交成本不在内。
- 缓存键量化后兵动画的肉眼观感只做了数据层面的检查，没有逐帧看截图对比。
- 回放哈希只覆盖 20 秒和这三个关卡；更长战斗、Boss 关、塔模式没有逐位对比。
